# Phase 3 — Baseline Synthesis and Implementation Measurement

## Objective

Measure the verified baseline on a real FPGA device so that simulation latency is separated from implementation timing. Do not modify the verified baseline RTL for this measurement.

## Required inputs

- FPGA vendor/device: select and record the exact part number before synthesis.
- Vendor synthesis tool matching the selected device.
- Existing baseline RTL and testbench.
- The functional reference remains the 1,000-vector golden run already recorded in `docs/PHASE2_VERIFICATION.md`.

## Metrics to record

### Timing
- Achieved Fmax
- Worst negative slack (WNS)
- Total negative slack (TNS)
- Critical-path startpoint/endpoint
- Critical-path delay
- Clock period

### Resources
- LUT / ALM / logic utilization
- Flip-flops / registers
- BRAM / block memory
- DSP blocks
- Other device-specific memory or logic resources

### Latency

Keep the existing RX-to-TX cycle measurement. Convert cycles to nanoseconds only after the implemented clock period is known:

`latency_ns = latency_cycles × clock_period_ns`

Do not treat the current 1-cycle ModelSim result as an FPGA timing result.

## Fair-comparison rule

Every architecture must use the same FPGA device, clock constraint, input workload, measurement boundary, and functional golden vectors. Record tool version and synthesis settings for every run.

## First run

1. Select the FPGA device and record its exact part number.
2. Create a vendor synthesis project containing:
   - `rtl/baseline/order_book.sv`
   - `rtl/baseline/baseline_market_pipeline.sv`
3. Add a clock constraint for the chosen target.
4. Synthesize and implement without optimization changes intended specifically to improve the baseline.
5. Record timing and resource reports.
6. Archive the reports under `docs/results/`.
7. Only after the baseline measurement is reproducible, begin the streaming architecture.
